# Merchant OS — Existing Agent → AI Employee Mapping\n\nSnapshot: 2026-09-24\nBranch: sales-page-v1\n\n## Purpose\n\nThis document maps the agents and agent-like components that already exist in the repository to the reusable AI Employee architecture. It does not create new agents, integrations, providers, or production capabilities.\n\nTarget flow:\n\nChannel / User → Router / Supervisor → Specialist Employee → Typed Tool / Adapter → Control Plane → Commerce Core → Events / Audit\n\nCore rule: the model/agent proposes; the Control Plane validates; Commerce Core executes.\n\n## 1. Existing Professor OS specialist chain\n\nThe repository already contains a concrete 10-specialist chain in specialists.py, orchestrated by ProfessorOS.\n\n| Existing component | Current responsibility | AI Employee role | Maturity |\n|---|---|---|---|\n| ResearchAgent | Merchant evidence, discovery and enrichment | Research / Sourcing Employee | Implemented |\n| IntelligenceAgent | Merchant scoring from observable signals | Intelligence Employee | Implemented |\n| DataAgent | Data quality, market signals, outcomes, gaps and hypotheses | Data / Intelligence Employee | Implemented |\n| MarketAgent | Market analysis context | Market Intelligence Employee | Implemented, lightweight |\n| CustomerAgent | Customer profile/taxonomy enrichment | Customer Intelligence Employee | Implemented |\n| SalesAgent | Sales/channel signals from research | Sales Employee | Implemented, lightweight |\n| StrategyAgent | Evidence-backed strategic proposals | Strategy Employee | Implemented |\n| VerificationAgent | Evidence validation | Verification / Quality Employee | Implemented |\n| ExecutionAgent | Dispatches approved execution through AgentNetwork | Execution Employee | Implemented with gate |\n| SupervisorAgent | Mission veto/review | Supervisor / Governance Employee | Implemented |\n\nCurrent Professor sequence:\n\nresearch → intelligence → data → market → customer → sales → strategy → verification → execution → supervisor\n\nThis is already the strongest reusable orchestration foundation in Merchant OS. Do not create another parallel specialist framework.\n\n## 2. Existing customer-facing agent layer\n\nagents.py already contains:\n\n| Component | Responsibility | AI Employee mapping |\n|---|---|---|\n| sales_agent | Price and purchase intent responses | Customer Concierge / Sales Employee |\n| order_agent | Order-status response | Order Employee |\n| customer_agent | General customer support | Customer Concierge |\n| human_handoff | Escalation to human support | Human Handoff |\n| general_router | Fallback routing | Supervisor / Router |\n\nrouter.py maps intents to these handlers.\n\nThese handlers are conversation/router prototypes, not owners of Commerce truth. They must not bypass commerce_service.py, commerce_agent.py, identity checks, approval gates, or Commerce Core.\n\n## 3. AgentRuntime and Professor OS\n\nagent_runtime.py provides the reusable runtime substrate: AgentTask, AgentResult, AgentDefinition, registry/dispatch, parent task linkage, audit, and agent memory.\n\nprofessor_os.py provides orchestration: specialist registration, sequential execution, shared mission context, evidence verification, JEV decisioning, confidence/risk gates, supervisor veto, and mission memory.\n\nThis maps directly to the Supervisor / Orchestrator layer of the AI Employee architecture.\n\n## 4. Existing intelligence capabilities\n\nCustomer side already includes:\n\n- CustomerDiscoveryAgent: public demand discovery and purchase-intent evidence.\n- CustomerIntentEngine: explainable intent extraction.\n- CustomerInterestEngine: category/product interest and purchase readiness.\n- CustomerVoiceEngine: feedback themes and sentiment.\n- TargetedOfferEngine: customer-to-product matching and offer preparation.\n\nTogether these form most of the Customer Intelligence / Sales / Retention capability without creating duplicate agents.\n\nMerchant side already includes:\n\n- ResearchAgent: merchant discovery/evidence.\n- MerchantIntelligenceEngine: merchant ranking/signals.\n- DataAgent / DataIntelligenceAgent: data quality, demand/supply signals, gaps and hypotheses.\n- StrategicDeveloperAgent: evidence-backed development proposals.\n\nTogether these cover much of the Merchant Growth Employee concept.\n\n## 5. Existing creative and offer capabilities\n\nAlready present:\n\n- ProductCreativeEngine\n- OfferLearningEngine\n- TargetedOfferEngine\n- OfferDeliveryAdapter\n\nCorrect placement:\n\nSales / Marketing Employee → Creative + Offer Engines → Offer Guard / Control → Delivery Adapter → External Channel\n\nThese are capabilities/tools, not reasons to create four autonomous agents.\n\n## 6. Existing Commerce Core capabilities\n\nThe deterministic Commerce Core already contains catalog, offers, carts, quote, checkout, orders, cancellation, fulfillment, delivery, settlement, commerce errors, actor/identity context, and audit/events.\n\nAI Employee examples:\n\n| Employee intent | Existing Core capability |\n|---|---|\n| Search product | catalog |\n| Check offer | offers / offer lifecycle |\n| Build cart | cart service |\n| Calculate total/delivery | quote service |\n| Create order | checkout service |\n| Check order | order lifecycle / commerce service |\n| Cancel eligible order | cancellation service |\n| Track fulfillment | fulfillment/delivery core |\n| Settlement information | settlement service |\n| Merchant weekly report | intelligence + metrics + commerce data |\n\nNo AI agent should directly mutate SQLite tables.\n\n## 7. Existing execution boundary\n\nAgentNetwork currently exposes business-agent names: merchant_scout, merchant_research, outreach, product, sales, order, operations.\n\nArchitecturally it belongs behind the Control Plane:\n\nAI Employee → Proposal → Approval / Policy / Scope → AgentNetwork or Commerce Service → Execution → Audit / Events\n\nDo not expand this list with new autonomous agents merely to match the employee taxonomy.\n\n## 8. Existing WhatsApp capability\n\nThe repository already contains intake.py for inbound WhatsApp/customer message persistence, whatsapp.py for direct WhatsApp Cloud API outbound messaging, webhook.py for webhook handling, and WhatsApp/webhook tests.\n\nTherefore WhatsApp is not an empty capability gap.\n\nHowever, whatsapp.py is a direct Meta API client and predates the newer replaceable adapter boundary. It should be treated as legacy integration code to audit/reconcile later, not duplicated by another WhatsApp implementation.\n\nDesired boundary:\n\nWhatsApp → WhatsApp Adapter → Channel-neutral message contract → Router / AI Employee → Control Plane → Commerce Core\n\nNo Meta/MCP integration is added by this mapping.\n\n## 9. Reusable employee role matrix\n\n### Supervisor / Router\nExisting: ProfessorOS, SupervisorAgent, router.py, agents.py, CommerceControlPlane.\nRole: route work, apply confidence/risk gates, require verification/approval, prevent unauthorized execution, hand off to humans.\n\n### Customer Concierge / Sales\nExisting: sales_agent, customer_agent, CustomerIntentEngine, CustomerInterestEngine, CustomerVoiceEngine, TargetedOfferEngine, ProductCreativeEngine.\nRole: understand intent, answer product questions, surface relevant products, prepare offers, move qualified demand toward cart/checkout. Execution stays in Commerce Core.\n\n### Order Employee\nExisting: order_agent, cart/quote/checkout services, order lifecycle, cancellation service, delivery/fulfillment core.\nRole: order status, cart/order workflow, eligible cancellation, fulfillment status. Sensitive mutations remain gated.\n\n### Merchant Growth\nExisting: ResearchAgent, MerchantIntelligenceEngine, DataAgent, StrategyAgent, StrategicDeveloperAgent, OfferLearningEngine.\nRole: find merchants, understand supply, identify weak/strong products, identify market gaps, produce evidence-backed growth actions, learn from outcomes.\n\n### Intelligence\nExisting: DataIntelligenceAgent, MerchantIntelligenceEngine, CustomerIntentEngine, CustomerInterestEngine, CustomerVoiceEngine, MetricsEngine.\nRole: metrics, demand/supply signals, cohorts, anomalies, blind spots, hypotheses, evidence requirements.\n\n### Verification / Quality\nExisting: VerificationAgent, verify_evidence, Commerce Control Plane evidence records, AgentRuntime audit.\nRole: validate evidence, attach test/action evidence, protect verified memory, preserve auditability.\n\n### Execution\nExisting: ExecutionAgent, AgentNetwork, ActionEngine, CommerceControlPlane, Commerce services.\nRole: execute only after authorization, use typed tools/services, reject forged approval booleans, record execution evidence.\n\n## 10. Built vs reconciliation gates\n\nAlready present: agent runtime, 10-specialist Professor chain, research/discovery, merchant intelligence, customer intelligence, data intelligence, strategy proposals, verification, execution gate, supervisor veto, agent memory/audit, commerce control plane, deterministic Commerce Core, customer-facing routing prototype, creative/offer engines, and WhatsApp inbound/outbound legacy capability.\n\nRequires reconciliation: AgentNetwork business names vs employee taxonomy; direct whatsapp.py vs replaceable adapter boundary; legacy operations.py money/delivery/settlement paths vs newer Phase A Commerce Core; simple agents.py handlers vs authoritative Commerce Employee tools.\n\nNot authorized by this mapping: new autonomous agents, new LLM provider, WhatsApp MCP dependency, Meta production integration changes, external outbound campaigns, autonomous negotiation, autonomous settlement/payment, direct agent database mutation, automatic code/policy self-modification, or new mobile apps.\n\n## 11. Reuse rule for future verticals\n\nAuto parts, food, spices, clothing, hotels and other verticals should reuse the same employee layer.\n\nThe vertical supplies taxonomy, catalog, business rules, delivery policy, merchant policy, customer context, and channel adapters.\n\nThe reusable employee layer remains: Research, Intelligence, Customer, Sales, Order, Strategy, Verification, Execution, Supervisor.\n\nThis keeps Merchant OS a Commerce OS rather than a single-sector application.\n\n## 12. Next engineering step when Codex is available\n\nDo not create new agents.\n\nRun a reconciliation pass:\n\n1. Inventory every current agent/engine.\n2. Identify duplicate responsibilities.\n3. Classify each component as employee, specialist, tool, adapter, or control-plane component.\n4. Route sensitive Commerce actions through CommerceControlPlane / commerce_service.py.\n5. Preserve existing tests and add only missing mapping/contract tests.\n6. Audit legacy WhatsApp and operations paths against the newer Commerce Core.\n7. Run the full test suite, migrations, database integrity/FK checks, and git diff --check.\n\n## Bottom line\n\nMerchant OS already has most of the conceptual AI Employee workforce. The important work is consolidation and governance, not multiplying agents.\n\nThe existing 10-specialist Professor chain plus the customer-facing agents and domain engines can form the reusable employee layer, while Commerce Core remains the deterministic source of truth.\n\n
